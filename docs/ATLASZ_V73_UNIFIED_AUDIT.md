## 1. Executive summary

- 150 source items audited one by one (10 groups x 15); original identifiers preserved in `docs/audit/pkg150_source_ids.json`; cross-package references use `PKG150-<id>`.
- Result: **6 covered by a registry item that is already VERIFIED_WORKING, 98 partial, 30 missing, 16 external blocker** (sum 150).
- Evidence levels: 44 items map to modules that registry items cite with existing tests (fakes/sandbox, **not re-run for this audit**); 64 rest on source inspection only; 42 have nothing in the repository.
- 85 original capabilities unchanged: 18 VERIFIED_WORKING / 44 PARTIAL / 1 MISSING / 22 EXTERNAL_BLOCKER. Nothing here promotes a status.
- 23-point package (23 items): 1 covered by a verified registry item (12 Scheduled work), 16 partial, 6 missing (2 malware defense, 6 Ollama, 7 chat providers, 9 FTS5, 10 semantic search, 16 agent messaging). Global Business package: see section 7.
- **Nothing in the 150 is LIVE.** No live model provider, source, browser, voice, vision or payment rail is connected. "Covered" means only that a registry capability already VERIFIED by independent rounds addresses it within its tested scope; it is still sandbox/fake-provider evidence.
- Many of the 150 are duplicates or near-duplicates of each other and of the 85 (section 6). The real number of distinct missing building blocks is far smaller than the count of missing rows.

### Evidence limits (read this before relying on any row)

1. This audit is **source inspection plus registry lookup**. No test, probe or mutation run was executed for any of the 150 items. The last real test run (1090/1090, 52/52 probes) covers the existing code, not these requirements.
2. Classification rules: C = a VERIFIED_WORKING registry item covers it; P = something of the capability itself exists; M = nothing of the capability itself exists (prerequisites may); E = its core needs a live provider, data source, hardware or approval that is not connected and no deterministic implementation exists.
3. Judgement calls are mine and reviewable: the CSV lists modules and the rule behind each row. Module headers were read for the main modules; for others only the name/grep hits were used (marked S).
4. Vendor attributions in the 150 titles (GPT, Claude, Merlin, Grok, Gemini) are the owner's idea labels; no vendor feature claim is verified or relied on.
5. Registry rule stands: a registry entry is not proof; VERIFIED_WORKING needs independent evidence and the owner's confirmation.

## 2. Identifier conflicts and namespacing

- The 150 package uses `GE01`-`GE15` (Gemini group). The 85-capability registry already has `GE01`-`GE13`. Source identifiers are kept as written; cross-package tracking uses **`PKG150-GE01` ... `PKG150-GE15`**. Registry rows were not renamed.
- Other prefixes (S, AS, OP, SN, HK, MR, GR, O5, S5) do not clash with registry capability IDs. `S01`-`S15` are distinct from the registry requirement IDs `V73-S##-###`, but the namespacing is applied to all 150 for consistency.
- Registry capabilities with IDs `M`, `C`, `G`, `A`, `P` (e.g. `P07`) are always written without the `PKG150-` prefix.
